Configuration

About 4 min

Configuration

We configure a study by writing one YAML file, conventionally conf/atlas.yaml. Everything we set goes under a top-level atlas: key.

Minimal Example

Copy this in and edit it for the recipe:

atlas:
  study_name: mini_an4_ci_check
  study_dir: exp/atlas/mini_an4_ci_check
  application: hyperparameter_search
  objective_file: program.md

  task: ASR
  dataset: mini_an4
  model: transformer
  year: 2026

  recipe:
    training_config: conf/training_asr_transformer.yaml
    inference_config: conf/inference.yaml
    metrics_config: conf/metrics.yaml

  metric:
    name: wer
    mode: min
    extraction:
      - path: "inference/metrics.json"
        name: wer
        key: "espnet3.systems.esp2_asr.metrics.wer.WER.test.WER"

  budget:
    max_trials: 20

  agent:
    provider: claude

  submission:
    resources: {}

  search_space:
    allowed_keys:
      - trainer.*
      - optimizer.*
    denied_keys:
      - data.*
      - output_dir

Study Identity

KeySet it toWhy
study_namea unique idUsed as the state-table key and job-name prefix (ar-<study_name>-...).
study_dirwhere we want resultsATLAS freezes the config/graph there and writes trials/state under it. Relative paths resolve against --recipe-dir.
applicationhyperparameter_search, architecture_search, or our own graph pathPicks which loop ATLAS runs. See Graphs and stages.
objective_fileour objective file's pathATLAS copies it to study_dir/program.md when we run init.
task / dataset / model / yearwhatever we likeFree-form metadata; ATLAS doesn't read these.

Recipe

atlas:
  recipe:
    training_config: conf/training_asr_transformer.yaml
    inference_config: conf/inference.yaml
    metrics_config: conf/metrics.yaml

For every trial, ATLAS patches training_config with the agent's dotted-key changes (e.g. optimizer.lr: 3e-4) and resolves it to trials/<trial_id>/resolved_training_config.yaml. It treats inference_config and metrics_config as fixed — only runtime paths get substituted, so we don't need to worry about the agent touching evaluation.

Metric

atlas:
  metric:
    name: wer
    mode: min      # or "max"
    extraction:
      - path: "inference/metrics.json"   # relative to the trial dir
        name: wer
        key: "espnet3.systems.esp2_asr.metrics.wer.WER.test.WER"

ATLAS reads extraction[].path as JSON after each trial and pulls extraction[].key (a dotted path) out as extraction[].name. We make metric.name match one of those names, and set metric.mode to min or max so ATLAS knows which direction counts as an improvement. We can add more extraction entries to record extra metrics alongside the one we're optimizing.

Search Budget

atlas:
  budget:
    max_trials: 20            # hard cap on proposed trials
    max_parallel_trials: 1    # concurrent running trials (default 1)
    max_failures: 10          # stop after this many failed/timeout trials
    no_improve_stop: 10       # stop after this many trials with no new best

Set any of these and ATLAS stops once it's hit. Leave one unset (or 0) to disable that trigger — usually we only need to set max_trials.

Early Stop

atlas:
  early_stopping:
    enabled: true
    epoch_interval: 1              # check every N epochs
    # iteration_interval: 500      # mutually exclusive with epoch_interval
    # elapsed_time_interval_sec: 1800

Turn this on and the agent checks a running trial's curve at the keypoints we pick (epoch, iteration, or elapsed time — choose one) and can stop it early if it looks unpromising. The training job itself does these checks — there's no separate controller to set up for this to work.

Agent

atlas:
  agent:
    provider: claude   # or "codex"
    claude:
      model: null              # use the CLI's default model
      permission_mode: bypassPermissions
      effort: null
    codex:
      model: null
      sandbox: workspace-write

Whichever we pick, ATLAS routes every call — propose, debug, reflect, summarize — through that one CLI.

Local model instead of the hosted one

Both CLIs can point at a local/self-hosted OpenAI- or Anthropic-compatible endpoint instead of the default hosted model.

For Codex, we add the provider through -c overrides and select it:

atlas:
  agent:
    provider: codex
    codex:
      model: my-local-model
      config:
        model_provider: local
        model_providers.local.name: "Local"
        model_providers.local.base_url: "http://localhost:8000/v1"
        model_providers.local.wire_api: "chat"

For Claude Code, we point it at the endpoint through environment variables instead, since claude reads ANTHROPIC_BASE_URL for this:

atlas:
  agent:
    provider: claude
    env:
      ANTHROPIC_BASE_URL: "http://localhost:8000"
      ANTHROPIC_API_KEY: "local-placeholder-key"
    claude:
      model: my-local-model

Submission

atlas:
  submission:
    resources:
      gpus: 1
      cpus: 4
      mem: 32G
      time: "08:00:00"
      extra:
        partition: gpuA100x4
    instructions: |
      A free-form note the agent reads for this cluster's job-submission
      conventions (which submit_*.sh, or a raw sbatch/qsub template).
    controller:
      run_in: local        # "local" (default) or "queue"
      handoff_after_sec: 3600

  • Set resources to the study-level default; override it on a single graph node if that node needs something different.

  • Write instructions if controller.run_in: queue — ATLAS needs it to submit jobs on our cluster. Skip it and keep run_in: local to just run everything as a local subprocess (fine for CI or a single machine).

  • instructions isn't limited to Slurm/PBS: the agent reads it and writes the actual submission code itself, so we can describe any in-house or unusual scheduler here, e.g.:

    atlas:
  submission:
    instructions: |
      This cluster has no Slurm/PBS. Submit jobs with our internal CLI:
        mycluster-submit --gpus {gpus} --mem {mem} --time {time} \
          --cmd "{command}" --stdout {stdout} --stderr {stderr}
      It prints "job_id: <id>" on success; poll status with
        mycluster-status <id>   # prints RUNNING / DONE / FAILED
      Treat FAILED and a missing job id as submission failure.

  • Choose controller.run_in:

    • local — we run espnet3 atlas run ourselves as the controller loop (keep it alive in tmux/screen).
    • queue — ATLAS submits the controller as a tick job that resubmits its own successor before its walltime runs out, so we don't have to babysit it. See Running a study.

Search Space

atlas:
  search_space:
    allowed_keys:
      - trainer.*
      - optimizer.*
      - model.peft.*
    denied_keys:
      - data.*
      - output_dir
      - collect_stats_dir
      - recipe_dir
      - exp_dir
      - stats_dir
      - inference_dir

ATLAS checks every key the agent proposes against allowed_keys first (it must match at least one) and then denied_keys (a match here always wins). We always deny the runtime-injected keys (recipe_dir, data_dir, exp_tag, exp_dir) — ATLAS sets those itself. If the allowed/denied lists wipe out the whole patch, ATLAS rejects the trial rather than running an empty change.

Trial

atlas:
  trial:
    timeout_sec: 86400          # default: 1 day
    command_template: null      # advanced: override train/infer/measure

By default ATLAS runs run.py --stages train, then infer, then measure for us, resuming from exp/last.ckpt and skipping stages already done. If our workload doesn't fit that train/infer/measure shape, we set command_template to our own argv list instead:

atlas:
  trial:
    command_template:
      - python3
      - run.py
      - --stages
      - train
      - infer
      - measure
      - --training_config
      - "{training_config}"
      - --inference_config
      - "{inference_config}"
      - --metrics_config
      - "{metrics_config}"

We can use these placeholders: {training_config}, {inference_config}, {metrics_config}, {trial_dir}, {attempt_dir}, {recipe_dir}.

Objective (program.md)

This is where we write for the agent, in plain text — not YAML. ATLAS copies it to study_dir/program.md and shows it to the agent on every call. We write:

  • our objective, and the metric/data split we're judging it on
  • what must not change, and why — so the agent doesn't "fix" a constraint we set on purpose
  • explicit boundaries, e.g. "don't read other recipes under egs3/"
  • for a long budget, an instruction to keep a research-plan checklist, so the agent explores broadly before narrowing in on one idea

Here's a real one, egs3/chime4/asr/program.md:

# AutoResearch Objective

Find LoRA fine-tuning hyperparameters that minimize WER for Whisper
large-v3 fine-tuned on the combined CHiME-4 + WSJ + AMI "topline"
training mix, evaluated on a fixed cross-domain dev subset.

## Fixed Setup
- Base model: large-v3 (OpenAI Whisper), LoRA adapter (frozen backbone).
- Training config: conf/finetune/whisper_lora_topline.yaml.
- Don't check other recipes under egs3/.

## Do Not Touch: batch_bins
dataloader.train.iter_factory.batches.batch_bins (2,000,000) was set
after real runs OOMed at 3,400,000. Do not raise it without
re-verifying with an actual training run first.

## Allowed Search Space
- optimizer.lr, optimizer.weight_decay
- model.peft.r, model.peft.lora_alpha, model.peft.lora_dropout
- scheduler.warmup_steps
- trainer.accumulate_grad_batches

## Evaluation And Acceptance
Treat the WER from the fixed dev subset as the metric to minimize.
